## 2. 攻击向量总表

下表按原文内容整理。检测难度是课程的粗略评价，不是固定分级。

| 向量 | 主要机制 | 原文检测难度 | 可能影响 |
| --- | --- | --- | --- |
| Pickle `__reduce__` | 文件包含重建时调用逻辑 | 中：可用 `pickletools` 检查 | 不安全加载时执行代码 |
| Keras Lambda / 自定义层 | 不可信架构或代码进入计算路径 | 中：检查架构 | 加载或推理过程的代码与行为风险 |
| Dependency confusion | 公开同名包替代内部依赖 | 低：关注来源与版本异常 | 包构建、安装或使用阶段的执行风险 |
| Typosquatting | 名称相近的错误包 | 低：名称对比 | 不可信包进入环境 |
| Repository manipulation | 假组织、专业模型说明或仓库操纵 | 中：检查信任与变更线索 | 将恶意产物分发给信任该来源的用户 |
| API provider compromise | 模型更新、密钥或模板问题 | 高：不能只靠本地文件扫描 | 行为变化、资源滥用或数据风险 |
| GGUF 权重后门 | 转换前权重已被微调操纵 | 高：文件格式检查不足 | 特定输入下异常分类或输出 |

## 3. 三个不要混淆的结论

### ① 检测难度低，不等于一眼就能发现

高版本或相近名字是线索，不是最终恶意判定。被入侵的合法包、镜像和仓库可能没有明显拼写问题。

### ② 换格式，不等于清除了模型行为风险

SafeTensors、GGUF 等不使用 pickle 的格式，能避开该类对象重建机制，但不自动解决外部架构代码、加载器漏洞或权重中的后门。

原文称 GGUF 权重风险没有静态分析工具可用，这过于绝对。更准确的是：**单纯的文件代码扫描不足以证明行为安全，还需来源与模型评估。**

### ③ API 风险不等于完全没有证据

虽然可能没有本地恶意权重可扫描，但版本信息、模板差异、调用日志、权限记录和行为基线仍能支持调查。

## 4. 为什么需要分层防御？

从各层分别约束：

1. **来源：** 模型、依赖、模板来自哪里？
2. **变更：** 本次版本或内容有什么不同？
3. **加载：** 是否执行不可信代码？
4. **权限：** 即使有问题，能访问和操作什么？
5. **行为：** 是否偏离固定测试集与业务规则？
6. **监控：** 是否有异常外联、调用或资源使用？

这些是基于本房间内容的复习框架，不是已经在当前环境部署的控制。
