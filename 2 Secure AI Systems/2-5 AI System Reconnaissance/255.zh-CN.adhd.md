例如：

```text
Jupyter Notebook 中的凭据
          ↓ 可用于访问

          ↓ 提供产物地址

```

**单条发现：** 某台 MLflow 服务器暴露在网络上。

**攻击面关系：** 谁能访问它、凭据在哪里、它又指向哪些资源？

## 1. AI 如何扩大传统攻击面？

**一句话重点：** 服务数量增加只是表面，服务之间的连接同样重要。

原文回顾了任务 2 中的组件与端口，并与传统 Web 应用作比较。它强调：端口数量不能完整反映风险，还要看内部通信路径。

### 服务之间可能有哪些连接？

- 推理服务从向量数据库读取特征或检索信息。
- 编排平台向模型注册表推送更新。
- Jupyter Notebook 连接多个服务。
- Prometheus 从服务中抓取监控指标。

### 两个容易混淆的监听地址

| 地址 | 通常表示什么？ |
| --- | --- |
| `127.0.0.1` | 仅监听本机回环接口 |
| `0.0.0.0` | 监听所有 IPv4 网络接口 |

原文用「组件从监听本机改为监听所有接口」说明暴露范围扩大的风险。

> **理解边界：** 监听 `0.0.0.0` 本身不代表整个内部网络或所有服务都能被访问；还要看路由、防火墙、认证和权限。应逐条验证连接。

### 需要关注的防护边界

不只看外部防火墙，也要检查：

- 内部服务之间的网络访问策略。
- 组件是否真正需要互相访问。
- 服务间是否有身份验证，例如 mTLS（双向 TLS）。

原文指出，过于宽松的网络策略与缺少服务间身份验证，会使这些连接成为风险传播路径。

## 2. 攻击者会记录哪些平台配置问题？

**一句话重点：** 不只要记录产品名称，还要记录它开放了什么能力，以及谁能使用。

### MLflow：默认凭据与产物处理风险

原文描述：

- MLflow 在 2.x 之前默认不提供身份验证。
- 加入认证功能后，原文称 `basic_auth.ini` 中的默认凭据问题关联 `CVE-2026-2635`。
- 原文称 `CVE-2026-2033` 涉及产物处理程序的目录遍历，并可导致未经身份验证的远程代码执行。
- 原文为上述两项漏洞均列出 **CVSS 9.8**。

> **版本提示：** 以上漏洞编号、机制、评分与版本描述均按原文保留，未核验。不能因为发现端口 `5000` 或识别出 MLflow，就认定存在这些漏洞。

### Kubeflow：未认证的仪表板与过大权限

原文描述的风险链：

```text
未配置 OIDC 身份验证的仪表板
          ↓
通过 LoadBalancer / NodePort 暴露
          ↓
访问者可以创建 Jupyter Notebook
          ↓
Notebook 使用权限过大的 Kubernetes 服务账号
          ↓
可能进一步访问集群资源
```

**重点：** 仪表板能否访问、能否创建资源、服务账号有多大权限，是需要分别确认的条件。

### TorchServe：模型管理 API

原文指出，`8081` 上的管理 API 可用于动态注册模型，并描述从外部 URL 加载 `.mar`（Model Archive，模型归档）文件的风险。

模型加载可能执行初始化代码，因此如果攻击者能提交恶意模型归档，就可能引出远程代码执行。

**要记录的关系：** 管理 API 访问权限 → 模型来源控制 → 加载时执行能力。

### SageMaker：Notebook 的互联网访问配置

原文提到：

```text
DirectInternetAccess: Enabled
```

并声称该设置意味着 Notebook 接受互联网入站连接；它还引用一份未在文件中附上来源的 2024 年报告，称 82% 的 SageMaker 使用组织至少有一个 Notebook 使用此配置。

> **概念提醒：** 不应仅凭 `DirectInternetAccess: Enabled` 就判断 Notebook 可被公网直接入站访问。互联网访问配置与公网可达性、认证是不同问题，需分别确认。上述比例为原文统计，未核验。

## 3. 为什么模型注册表是高价值目标？

**一句话重点：** 注册表能说明模型的来源、历史、状态与存储位置，不只是列出文件名。

### 模型血缘信息：模型从哪里来、经历了什么？

| 信息 | 可以回答什么问题？ |
| --- | --- |
| 模型名称 | 组织有哪些模型？ |
| 版本历史 | 模型经历了哪些迭代？ |
| 阶段标签 | 处于预发布、生产还是归档阶段？ |
| 创建时间 | 何时创建或更新？ |
| Run ID | 对应哪次训练运行及其元数据？ |
| Artifact URI | 实际模型产物存放在哪里？ |
| 贡献者用户 ID | 谁参与了模型创建？ |

一个未受保护的注册表，可能集中暴露大量 ML 产品资产信息。

### 原文引用的 IBM X-Force 模式

1. 在 Jupyter Notebook 中发现 MLflow 凭据。
2. 使用 **MLOKit** 查询模型注册表。
3. 根据产物信息获取模型文件。

**记忆点：** 注册表像一张索引，告诉访问者其他资产在哪里。

## 4. 供应链侦察：追踪外部依赖

**一句话重点：** AI 系统依赖令牌、软件包和外部模型，这些依赖也要画进地图。

### A. Hugging Face 令牌

原文列出的 GitHub 搜索语句：

```text
filename:.env HF_TOKEN
```

令牌还可能出现在：

- `.env` 文件。
- CI/CD 流水线日志。
- Kubernetes Secret 中。

原文描述，被盗令牌可能被用于访问组织的私有模型与数据集。

> **权限提示：** 实际能读什么、能否写入，取决于令牌作用域和账号权限；发现一个令牌不等于拥有全部读写权限。

### B. 依赖混淆

ML 项目的 `requirements.txt` 可能列出内部包，例如：

```text
company-data-utils
```

原文举例：如果公开 PyPI 上存在同名恶意包，且安装来源或优先级配置不当，流水线就可能安装错误的包。

一些 Kubeflow 流水线会在训练时构建容器并在线安装依赖。依赖混淆、拼写仿冒包或来源配置问题，可能使不可信代码进入训练环境。

**记忆点：** 内部包名相同，不代表包的来源可信；同名包存在本身也不等于一定会被安装。

### C. 模型下载来源

模型来源可能出现在：

- 配置文件。
- Notebook 单元格。
- 容器构建日志。

例如从 **Hugging Face Hub** 或 **PyTorch Hub** 下载模型的路径。

原文指出，如果上游来源被替换，或攻击者通过被盗令牌修改模型，就可能让下游使用被篡改的产物。

**把关系画出来：** 外部来源 → 下载或构建流程 → 内部模型 → 生产部署。

## 📌 5. MITRE ATLAS 对照表

**一句话重点：** 用统一编号描述活动，方便别人理解报告。

ATLAS 借鉴 ATT&CK 的组织方式，聚焦针对 AI 与机器学习系统的对抗威胁。

原文称，截至 2025 年末，框架包含 **15 个战术、66 个技术、46 个子技术**。这些是原文的时间点统计，未独立核验。

### 本课程的映射（按原文保留）

| 课程中的活动 | 原文 ATLAS 编号 | 原文名称及中文含义 |
| --- | --- | --- |
| 扫描 AI 服务端口、探测端点 | `AML.T0006` | Active Scanning：主动扫描 |
| 通过未受保护的 API 定位模型注册表和训练产物 | `AML.T0007` | Discover ML Artifacts：发现机器学习产物 |
| 发现暴露的 HF 令牌与被投毒的依赖 | `AML.T0010` | ML Supply Chain Compromise：机器学习供应链入侵 |
| 枚举 LLM 配置与 API 兼容性 | `AML.T0014` | Discover ML Model Family：发现机器学习模型家族 |
| 上述活动整体所属战术 | `AML.TA0002` | Reconnaissance：侦察 |

> **分类提醒：** 发现外部依赖或暴露令牌，说明存在风险线索，不代表供应链已经被入侵。上表为课程的教学映射；正式报告应区分「观察到的活动」「可能风险」和「已经发生的入侵」。

### 技术与战术怎么区分？

- **技术（Technique）：** 具体做了什么；本表编号形式为 `AML.T...`。
- **战术（Tactic）：** 这些活动服务于什么阶段或目标；本表编号形式为 `AML.TA...`。

例如：**主动扫描是具体方法；侦察是这些活动的整体目的。**

## 6. 案例：ShadowRay 活动

> 本节按原文叙述整理，关联编号为 `CVE-2023-48022`；规模、时间与行为细节未独立核验。

**一句话重点：** 从一个可访问的 AI 组件开始，风险可能扩展到凭据、云资源与计算能力。

### 原文中的起点

Ray 在 `8265` 上提供作业提交 API。原文称该接口按设计不要求认证，Anyscale 强调 Ray 应部署于可信网络边界内，并对相关 CVE 的认定持异议。

### 原文描述的攻击链

1. **发现：** 使用 Shodan 寻找公开暴露的 Ray 仪表板；原文称发现超过 230,000 个。
2. **提交作业：** 通过 `/api/jobs/` 提交恶意作业。
3. **主机侦察：** 查看 `/etc/passwd` 中的用户信息，并用 `printenv` 收集环境变量中的凭据线索。
4. **横向移动：** 使用获取到的云凭据访问其他资源。
5. **盗用算力：** 劫持 GPU 计算节点并部署 XMRig 挖矿程序。

原文还提到，将 CPU 使用率限制在 60%、将进程伪装成 Linux 内核工作进程，以降低被发现的概率。

### 原文中的 ShadowRay 2.0

原文称，自 2025 年末活跃的变体增加了：

- 使用 LLM 生成可适配的恶意载荷。
- 通过隐藏的 cron 任务和 systemd 服务维持访问。
- 在 GitLab 托管载荷，仓库被移除后转向 GitHub。
- 使用 TCP 耗尽工具 `sockstress` 攻击生产网站，使活动扩展为多用途僵尸网络。

### 与本课程有什么关系？

| 课程任务 | 案例中的对应阶段 |
| --- | --- |
| 任务 2：发现组件 | 找到暴露的仪表板 |
| 任务 3：识别指纹 | 确认服务是 Ray |
| 任务 4：枚举服务 | 确认 API 可访问、是否允许提交作业 |
| 任务 5：连接发现 | 分析凭据、云资源与算力之间的风险路径 |

**重点：** 服务暴露、功能权限和资源信任关系共同决定影响范围。
