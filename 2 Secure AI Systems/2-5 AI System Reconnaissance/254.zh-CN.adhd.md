## 1. MLflow：沿着 5 个步骤收集信息

**一句话重点：** MLflow 将实验、模型、训练记录与产物信息集中起来，并通过 REST API 提供访问。

原文建议：发现可访问的 MLflow 实例后，沿以下顺序枚举。

### 第 1 步：列出实验

```http
POST /api/2.0/mlflow/experiments/search
```

**关注：** 实验名称、内部 ID。

实验名称可能暴露项目代号和业务目标，例如：

- `fraud-detection-v3`：欺诈检测第 3 版。
- `rag-embeddings-tuning`：RAG 嵌入调优。
- `customer-churn-prototype`：客户流失预测原型。

### 第 2 步：列出已注册模型

```http
GET /api/2.0/mlflow/registered-models/list
```

**关注：** 模型清单、名称、描述和创建时间。

这些信息帮助你了解组织已构建并注册了哪些模型。

### 第 3 步：获取模型版本详情

```http
GET /api/2.0/mlflow/model-versions/search
```

**重点字段：**

- `source`：产物 URI，即模型文件的存储地址。
- `user_id`：创建该模型版本的用户 ID。
- 创建时间。
- 阶段标签：帮助区分生产与预发布模型。

原文中的存储地址示例：

```text
s3://internal-ml-models-corp/experiments/1/artifacts/
```

**记住：** 一个地址就可能把模型注册表与内部云存储联系起来。

### 第 4 步：搜索训练运行记录

```http
POST /api/2.0/mlflow/runs/search
```

原文称可提交空请求体或筛选条件来查询运行记录；实际请求所需字段需以目标版本为准。

**关注：** 超参数、训练指标、自定义标签。

标签尤其值得查看，可能包含：

- 内部项目代号。
- 关联私有源代码的 Git 提交哈希。
- 部署环境标识。

### 第 5 步：列出可下载产物

```http
GET /api/2.0/mlflow/artifacts/list
```

**关注：** 可供访问或下载的模型文件清单。

原文用这 5 类 API 调用说明如何建立机器学习资产清单。实际能看到多少内容，取决于权限、参数和分页等条件。

### 🧠 停一下：用一句话回忆

**实验 → 模型 → 版本 → 训练记录 → 模型文件。**

## 2. 推理服务器：获取模型的「输入说明书」

**一句话重点：** 元数据可以说明模型接受什么输入、返回什么输出。

### NVIDIA Triton

```http
GET /v2/models/<name>/config
```

原文列出的配置内容包括：

| 配置项 | 含义 |
| --- | --- |
| 输入张量名称 | 请求需要使用哪个输入名称 |
| 多维形状（shape） | 输入数据的维度结构 |
| 数据类型 | 如 `FP32`、`UINT64`、`INT8` |
| 最大批大小（max batch size） | 一次最多处理多少个样本 |
| 后端框架 | 如 `tensorflow_graphdef`、`pytorch_libtorch`、`onnxruntime` |

可以把它理解为拿到了数据库的结构说明：知道结构后，就能理解怎样构造有效请求。

### TensorFlow Serving

```http
GET /v1/models/<name>/metadata
```

返回类似的输入输出规格，包括张量的**名称、形状和数据类型（dtype）**。

**记忆点：** 模型名称告诉你「有什么」；模型配置告诉你「怎么调用」。

## 3. 向量数据库：了解 RAG 在索引什么

**一句话重点：** 集合、字段和向量配置能提供数据主题与嵌入处理方式的线索。

### Weaviate

| 端点 | 原文描述的信息 |
| --- | --- |
| `GET /v1/meta` | 服务器版本、已安装模块 |
| `GET /v1/schema` | 类定义、属性名称、向量化模块配置 |
| `/v1/graphql` | 在未启用身份验证的实例上进行查询及原文所述的模式内省 |

**关注 `vectoriser` 相关配置：** 它可能帮助判断系统使用的嵌入模块或模型。

### Qdrant

```http
GET /collections
GET /collections/<name>
```

- 第一个端点：列出集合名称。
- 第二个端点：查看向量维度、距离度量和点数量等信息。

**原文示例：**

```text
集合名称：internal-hr-policies
向量维度：768
点数量：50,000
```

这些信息可以帮助推测该 RAG 系统可能索引内部人力资源政策。

> **推断提醒：** 集合名称和向量维度只是线索，不能单独证明具体数据内容或嵌入模型身份。

### Chroma

原文指出，旧版本可能默认在无需身份验证的情况下暴露：

```http
GET /api/v1/collections
```

这属于**版本与配置相关**的描述，不能直接套用到所有 Chroma 实例。

## 4. Prometheus 指标：从监控信息理解部署

**一句话重点：** 不调用推理接口，也可能从指标端点了解模型运行情况。

模型服务器经常在专用端口暴露 `/metrics`：

- Triton：原文列出端口 `8002`。
- TorchServe：原文列出端口 `8082`。

### 指标可能包含什么？

- 当前加载的模型名称与版本。
- 推理请求数量、延迟百分位数。
- 正在处理的批大小。
- 每个模型的 GPU 显存使用情况。

### 能据此了解什么？

部署结构、哪些模型流量最大、GPU 容量线索，以及系统是否繁忙。

> **术语提醒：** 原文称其为「被动情报」。更准确地说，这里无需向推理 API 发请求，但读取 `/metrics` 本身仍然是在访问目标服务。

## 5. 调试接口：结构与错误信息也会泄露情报

### FastAPI 文档接口

基于 FastAPI 的 ML 服务可能自动提供：

```text
/docs
/openapi.json
```

它们可能公开：

- 各端点的请求与响应结构。
- 身份验证要求。
- 示例请求数据。

### MLflow GraphQL 与调试参数

原文提到，MLflow 的 `/graphql` 端点历史上曾出现绕过 REST API 身份验证控制的情况，并列出内部解析器：

```text
mlflowSearchRuns
mlflowGetRun
```

原文描述可能被提取的信息包括：

- 主机上的用户名。
- `mlflow.source.name` 标签中的源代码路径。
- 项目资产清单。

原文还提到，一些 AI 网关端点在附加以下参数后可能返回原始堆栈信息：

```text
?debug=true
?verbose=1
```

堆栈信息可能暴露文件系统路径、库版本，偶尔也可能包含凭据。

> **适用范围：** 这些是原文描述的历史或特定部署行为，不代表所有 MLflow 或 AI 网关都存在相同问题。

## 6. Jupyter Notebook：查找服务之间的连接线索

**一句话重点：** Notebook 中的代码和凭据，可能把多个服务连接起来。

### 运行中的内核

```http
GET /api/kernels
```

在未要求身份验证的实例上，原文描述该接口可返回：

- 内核名称。
- 内核 ID。
- 最近活动时间。

这些信息能提供运行活动的线索，但本身不足以确定正在执行的具体代码。

### 更关键的是 Notebook 单元格

原文指出，代码中可能直接保存：

- MLflow 用户名：`MLFLOW_TRACKING_USERNAME`。
- MLflow 密码：`MLFLOW_TRACKING_PASSWORD`。
- 云存储访问密钥。
- Hugging Face 令牌。

**风险链条：** 一个 Notebook 暴露凭据，可能进一步暴露整个 AI 技术栈中的其他服务。

## 7. 案例：IBM X-Force 的 ML 训练基础设施攻击链

> 以下按原文叙述翻译；年份、工具功能及案例细节未独立核验。

**一句话重点：** 服务间的信任关系和 Notebook 中的明文凭据，可能形成完整攻击链。

### 原文描述的过程

1. **钓鱼获取入口：** 针对数据科学家的钓鱼尝试，使攻击者获得 Azure ML 环境访问权限。
2. **Notebook 暴露凭据：** 攻击者在单元格中发现明文 MLflow 凭据。
3. **登录 MLflow：** 使用凭据运行 IBM X-Force Red 团队开发的 CLI 工具 **MLOKit**。
4. **自动枚举与获取模型信息：** 通过标准 REST API 请求访问模型清单、版本元数据与产物 URI。
5. **继续访问存储：** 沿着产物地址触及模型文件。

原文称 IBM X-Force Red 在 **2025 年**记录了这一攻击链。

### 将攻击链压缩成一行

**Jupyter Notebook（凭据） → MLflow Tracking Server（模型注册表） → S3（模型产物）**

三个组件，后一个组件信任前一个组件提供的访问凭据。

按原文分析，这条链的核心问题在于服务可访问、连接它们的凭据又保存在 Notebook 单元格中，而不一定需要利用软件漏洞。

### 原文列出的 MLOKit 功能

| 功能名 | 原文描述 |
| --- | --- |
| `list-models` | 列出已注册模型 |
| `download-model` | 获取模型，并涉及版本元数据和产物 URI |
| `list-notebooks` | 列出 Notebook |
| `add-notebook-trigger` | 通过生命周期配置实现代码执行 |
| `poison-model` | 覆盖模型产物 |

原文还称，该工具后来扩展到 SageMaker 等平台，并在 GitHub 开源。
