## 1. 阶段一：被动侦察

**核心：** 在直接接触目标网络前，先检查已经公开的信息。

### A. 搜索公开服务线索

原文建议在 Shodan、Censys 和 FOFA 中，结合组织 IP 范围搜索 AI 服务标识。下面是原文示例，具体平台语法可能不同。

**MLflow：**

```text
port:5000 "MLflow"
```

**Jupyter：**

```text
port:8888 title:"Home Page - Select or create a notebook"
```

**Ray：**

```text
http.title:"Ray Dashboard"
```

**注意：** 命中结果只是候选服务，不证明它无认证或存在漏洞。

### B. 搜索公开仓库中的凭据与配置

原文列出的搜索字符串：

```text
filename:.env MLFLOW_TRACKING_URI
filename:.env HF_TOKEN
filename:config.json model_name site:github.com
```

它们分别提供 MLflow 连接配置、Hugging Face 令牌、模型名称等线索。最后一条混合了文件条件与站点限定，应按实际搜索平台调整语法。

### C. 阅读公开研究和工程资料

检查 arXiv 论文与工程博客，寻找已公布的模型架构、框架和部署方式。

原文将此映射到：

```text

```

这是原文映射，未在本次翻译中独立核验。

### D. 检查容器镜像与招聘信息

- Docker Hub、GitHub Container Registry 中的组织镜像可能包含配置线索。
- 招聘「MLflow Administrator」或「Kubeflow Platform Engineer」，可能透露技术栈。

**本阶段产出：** 候选服务、技术栈、配置、外部依赖及其公开来源。

## 2. 阶段二：主动扫描

**核心：** 检查已授权目标上的 AI 相关端口。

### 原文 Nmap 命令

```bash
nmap -p 5000,6333,8000,8001,8002,8080,8265,8500,8501,8888,9000,11434,19530 -sV --script=http-title,http-headers <target>
```

**`<target>` 是占位符，要替换后再运行。**

下面是使用 Cyphira 实验子网的可复制版本：

```bash
nmap -p 5000,6333,8000,8001,8002,8080,8265,8500,8501,8888,9000,11434,19530 -sV --script=http-title,http-headers 10.10.45.0/24
```

| 参数 | 用途 |
| --- | --- |
| `-p` | 指定端口 |
| `-sV` | 探测服务与版本 |
| `--script=http-title,http-headers` | 尝试读取 HTTP 标题与响应头 |

### 不要漏掉两类服务

**① gRPC**

- Triton 常见参考端口：`8001`。
- TensorFlow Serving 常见参考端口：`8500`。
- Nmap 可能只给出通用结果，需要进一步检查。

Cyphira 已知主机的查询示例：

```bash
grpcurl -plaintext 10.10.45.15:8001 list
```

需要目标支持并允许 gRPC 反射访问；`-plaintext` 表示不使用 TLS。

**② 监控指标**

- 常见路径：`/metrics`。
- Triton 原文端口：`8002`。
- TorchServe 原文端口：`8082`。

原文扫描列表没有包含全部参考端口，例如 `6334`、`8081`、`8082` 和 `9001`，因此这条命令不能保证发现所有 AI 服务。

**本阶段产出：** 主机、端口、候选服务及后续确认计划。

## 3. 阶段三：API 指纹识别

**核心：** 根据路径、响应头、JSON 和错误信息确认框架。

原文建议使用 ffuf 或 feroxbuster，配合 AI 专用路径字典检查已发现的 HTTP 服务。

### 路径字典

```text
/v1/models
/v2/models
/v2/health/ready
/api/2.0/mlflow/experiments/list
/api/2.0/mlflow/registered-models/list
/pipeline/apis/v1beta1/pipelines
/api/serve/deployments/
/v1/schema
/v1/meta
/api/kernels
/api/contents
/openapi.json
/docs
/graphql
/metrics
/api/tags
/api/show
/collections
/healthz
/ping
```

### 收到响应后，按这个顺序看

1. **响应头：** 有没有产品标识？
2. **响应正文：** JSON 字段是否具有框架特征？
3. **错误信息：** 字段、类型要求或命名空间提供了什么线索？

原文以 HTTP `200` 作为进一步分析的起点。但 `200` 也可能是统一首页；`401`、`403`、`405` 等响应也能提供线索。某些端点还需要 POST 和参数，不能只用 GET 判断是否存在。

### Cyphira 手动检查示例

```bash
curl -i http://10.10.45.12:5000/
```

```bash
curl -i http://10.10.45.15:8000/v2/models
```

`-i` 同时显示响应头与正文。服务身份应由多个证据相互印证。

**本阶段产出：** 框架身份、证据、尚未确认的部分。

## 4. 阶段四：元数据提取

**核心：** 确认服务后，再查模型、数据、存储和用户之间的关系。

| 服务 | 原文要求收集的信息 |
| --- | --- |
| MLflow | 实验、注册模型、模型版本、产物 URI、用户 ID、训练记录与产物清单 |
| Triton / TensorFlow Serving | 张量规格、模型配置、后端框架 |
| 向量数据库 | 集合、字段结构、数据主题与嵌入配置线索 |
| Jupyter | 内核列表、Notebook 单元格、明文凭据线索 |

原文将 MLflow 枚举概括为五类 API 调用。实际可见范围取决于权限、参数、分页与版本，不能保证五次请求就覆盖所有资产。

### 代理英文指令：整理元数据

```text
Summarize the metadata returned by the confirmed Cyphira AI services. List experiments, models, versions, artifact URIs, user IDs, tensor specifications, vector database collections, and notebook credential clues. Separate observed facts from assumptions.
```

**本阶段产出：** 有来源证据的元数据清单，以及组件之间的联系。

## 5. 阶段五：供应链审查

**核心：** 追踪外部模型、软件包、存储与镜像来源。

### 一次检查一项

- [ ] 配置、Notebook 和构建日志中有哪些模型下载来源？
- [ ] S3、GCS 或 MinIO 中的模型产物是否被意外公开？
- [ ] `requirements.txt` 和 `Pipfile` 是否包含内部包名？
- [ ] 包来源或解析策略是否可能引入同名或仿冒包？
- [ ] 容器镜像是否允许未经授权的拉取？

**注意：** 某个内部包名在 PyPI 上未注册，不等于一定存在可利用的依赖混淆；还需看安装配置和来源优先级。

### 代理英文指令：检查依赖联系

```text
Review the Cyphira findings for supply chain risks. Identify external model sources, Hugging Face token clues, artifact storage locations, internal package dependencies, and container image access. Explain the relationships and identify which risks still need verification.
```

**本阶段产出：** 依赖关系、暴露条件和待验证风险。

## 👀 7. 从防守方看：侦察会留下什么？

**核心：** 日志模式是调查线索；没有 UI 会话或请求次数多，都不自动等于攻击。

### 模式 A：反复枚举模型

**原文描述：** 单个 IP 在几秒内对 `/v2/models` 发出 10～50 次连续 GET 请求。

**调查方向：** 是模型清单脚本、健康检查、管理平台，还是异常枚举？结合来源、频率和历史基线判断。

### 模式 B：脚本化访问 MLflow

```text
/api/2.0/mlflow/registered-models/list
/api/2.0/mlflow/model-versions/search
```

**原文描述：** 同一来源请求这些 API，却没有对应 UI 会话，符合 MLOKit 的访问模式。

**重要区别：** 合法 SDK、自动化任务和其他工具也可能直接调用 API。这个模式不能唯一识别 MLOKit，UI cookie 也不是判断脚本是否恶意的充分依据。

### 模式 C：监控范围之外读取指标

```text
/metrics
```

**原文描述：** 来源不在已知监控 CIDR 范围中。

**调查方向：** 核对监控资产清单、代理与新接入系统；确认未知来源是否确实未经授权。

### 模式 D：集中扫描 AI 端口

```text
5000,8000,8001,8080,8265,8888
```

同一来源依次探测这些端口，可能意味着针对 AI 基础设施的发现活动。还需排除授权资产扫描与安全评估。

### 模式 E：MLflow 产物路径中的遍历字符

```text
../
%2e%2e%2f
```

原文将其与探测 `CVE-2026-2033` 关联。编号与漏洞细节未核验；路径遍历特征本身也不能唯一定位某个 CVE，更不证明利用成功。

### 模式 F：没有可见 UI 会话的 Jupyter API 请求

```text
/api/kernels
/api/contents
```

原文将没有有效 session cookie 的请求视为异常线索。但 API 也可能使用令牌或其他认证方式，应同时检查认证结果、调用身份、来源与读取范围。

### 快速判断表

| 观察到的行为 | 初步分类 | 还应核对什么？ |
| --- | --- | --- |
| 连续访问多个 AI 端口 | 主动扫描 | 来源是否为批准的扫描器 |
| 查看响应头、模型接口和错误 | API 指纹识别 | 是否为正常调试或资产检查 |
| 读取版本、用户与产物地址 | 元数据提取 | 调用身份、权限、业务用途 |
| 查询外部模型来源或存储策略 | 供应链审查 | 是否为批准的审计流程 |
| 已知 Prometheus 定时读取指标 | 可能是正常监控 | 来源、频率和路径是否符合基线 |

被动侦察通常不直接访问目标内部网络，因此不一定会在目标 SIEM 中产生明显记录。

## 🛡️ 8. 快速缩小暴露面的措施

**核心：** 先收紧身份验证、权限和网络可达性，再减少不必要的信息输出。

### ① 启用 MLflow 身份验证

原文重点措施：

```text
Enable MLflow authentication
```

原文同时列出：

```text
MLFLOW_TRACKING_USERNAME
MLFLOW_TRACKING_PASSWORD
```

**配置提醒：** 设置客户端使用的用户名和密码变量，不等于服务端已经强制认证。要确认服务端认证配置或认证反向代理实际生效，并验证未认证请求无法读取受保护信息。

### ② 收紧 Jupyter 的运行与访问配置

原文建议在生产中避免不必要地使用：

```text
--allow-root
--ip=0.0.0.0
```

同时要求令牌认证，并通过 VPN、入口认证或网络策略限制访问。

**区分：** `--allow-root` 涉及运行用户；`--ip=0.0.0.0` 涉及监听接口。移除参数本身不保证认证或网络隔离已落实。

### ③ 限制 AI 服务的网络入口

原文列出的重点端口：

```text
5000,8000,8001,8002,8080,8265,8500,8501,8888,9000
```

根据业务需要明确允许范围，避免意外向互联网开放管理、开发、存储或监控接口。

### ④ 限制 Triton 显式模型控制

原文参数：

```text
--model-control-mode none
```

原文用它说明减少模型加载和卸载管理能力。具体模式行为需结合版本和启动配置确认；该参数不替代整个推理服务的认证与网络控制。

### ⑤ 只允许监控系统访问指标

将 `/metrics` 限制到监控系统的来源网段，尤其关注 Triton `8002`、TorchServe `8082`。

### ⑥ 轮换并缩小 Hugging Face 令牌权限

使用细粒度令牌，仅授予所需资源与操作范围；只需读取时不要赋予写入能力。

### ⑦ 减少调试信息暴露

在响应到达不可信网络前，减少不必要的调试响应头、完整堆栈与详细错误信息。服务端仍应保留适当的诊断日志。

### ⑧ 检查模型存储桶策略

审查 MinIO、S3 中的模型产物访问策略，避免意外公开模型权重和相关文件。

## 9. 案例：Hugging Face Spaces 凭据泄露

> 原文案例时间为 2024 年 6 月；事件细节与官方建议未在本次翻译中核验。

### 原文描述

攻击者未经授权访问 Hugging Face Spaces 平台，并接触开发者为托管应用保存的认证秘密，其中包括可访问私有模型、数据集与配置的令牌。

原文将其与两个侦察阶段关联：

- **阶段 1：** 公开仓库、`.env` 和流水线日志可能暴露同类凭据。
- **阶段 5：** 被盗令牌可能影响外部模型和数据依赖。

### 原文提到的响应

撤销受影响令牌、迁移到细粒度令牌、缩小权限范围。

原文还概括为避免在应用秘密中保存令牌；不能据此理解为应该改用源码或明文配置。实际应使用适合的秘密管理、最小权限与轮换机制。

**权限提醒：** 有效令牌能做什么由其作用域决定，不是每个令牌都同时拥有全部资源的读写能力。

**学习重点：** 缩小令牌权限与及时轮换，能降低公开泄露和平台事件两类风险的影响。

## 🧪 10. 实验：Cyphira SOC Analyst

**场景：** 从侦察者切换到防守者，查看任务 2～5 的活动在 SIEM 中留下的记录。

打开 **Cyphira SOC Analyst** 代理。以下均为可直接复制的英文指令。

### ☐ 第 1 步：获取近期告警

```text
Show me the recent alerts from the Cyphira SIEM related to the AI infrastructure.
```

**你要看：** 来源 IP、时间、目标主机、端口、路径、方法、认证身份和响应状态等可用字段。

### ☐ 第 2 步：逐条分类

```text
Present the log entries one at a time. Ask me to identify the reconnaissance phase and the specific activity for each entry. Wait for my answer before continuing.
```

分类时使用这些英文阶段名称：

```text
Passive Reconnaissance
Active Scanning
API Fingerprinting
Metadata Extraction
Supply Chain Review
```

可用回答模板：

```text
Phase: Metadata Extraction
Activity: Scripted MLflow model enumeration
Evidence: Requests to registered-models/list and model-versions/search without a corresponding UI session
Assessment: Suspicious automation that requires verification of the source and identity
```

这是回答格式示例，不代表已经读取或分类了真实日志。

### ☐ 第 3 步：提出防护措施

```text
For each log pattern, ask me to recommend a quick win from Task 6. Help me distinguish controls that prevent access from controls that detect suspicious activity.
```

可用英文回答示例：

```text
Recommendation: Enable MLflow authentication and verify that unauthenticated requests cannot access protected metadata.
```

```text
Recommendation: Restrict metrics endpoints to the approved monitoring CIDR and investigate requests from other sources.
```

### ☐ 第 4 步：区分正常与可疑流量

```text
Mix legitimate operational traffic with suspicious reconnaissance patterns. Present one log entry at a time and ask me to explain whether it is expected, suspicious, or inconclusive, using the available evidence.
```

**不要仅凭一个字段下结论。** 结合已知监控来源、定时任务、授权扫描、认证信息和业务基线。
